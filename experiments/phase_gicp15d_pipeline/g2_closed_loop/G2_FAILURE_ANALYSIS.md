# G2_FAILURE_ANALYSIS

## F1 — 回放器不确定（本轮最重要的失败）

**现象。** 同一 `gicp15d_g0_service` 二进制、同一输入、同一命令，连跑两次（`det_a` / `det_b`，各 200 帧）：

| 量 | 两次运行之差 |
|---|---|
| matcher `final` 位姿 | p50 **0.0**，p95 **7.1e-15**，max **1.1e-13** m |
| EKF 后验 `p` | p50 **0.0807**，p95 **0.2725**，max **0.5265** m |
| 首个匹配器出现差异的帧 | 第 13 帧（1e-15 级） |
| 200 帧 RMSE（同参考） | a=1.7553，b=1.7430，**Δ=0.0123 m** |

**根因（源码级）。** `run_closed_loop.py`：

```python
latency = (time.perf_counter_ns() - start) / 1e6
...
advance(job_now + round(latency * 1e6))
event = dict(kind='ndt', header_ns=ref, ...)
replay.ingest(event)
```

`latency` 是**实测墙上时间**。`advance()` 把滤波器推进到"匹配完成时刻"，
之后才在历史时刻 `ref` 插入观测并重放。因此**匹配器的快慢决定了回放时摄入多少 IMU/Wheel**，
从而改变 `checkpoint(ref)` 的 P 与后验。

**影响。**
- 本轮的 1468 帧闭环只能视为该输入的**一次实现**，不是确定性结果。
- 任何两个闭环运行之间 <0.5 m 的差异都不能归因给匹配器。Phase AW 的
  0.596 vs 0.577 m 差 0.019 m，**远在噪声之下**。
- 这也解释了为什么匹配器逐字节相同而后验差 0.153 m（§3）。

**为什么本轮没有修。** 修它要改冻结的 AR 驱动器（`advance` 的目标时刻），
属于跨实验基线改动，会改变所有历史运行的可比性。按"最小变更 + 保留每阶段基线"，
本轮只定位与量化，并把修复列为下一阶段唯一阻塞项。

## F2 — 本轮评分不是签核管线

我用 `evaluation.npz` 的 `G_0.075` 与杆臂做了同口径打分，得到 3.0–3.4 m 量级，
而 AW 报告同一运行是 0.596 m。差异来自我的对齐/投影实现，不是数据。
**因此本报告不给出任何绝对精度结论**，只用同一实现做相对排序。

## F3 — 67 帧被拒（4.6%）

1468 帧中 67 帧 `NDT_NOT_CONVERGED_OR_INVALID`，集中在若干段，
最大观测中断 0.250 s（5 帧）。这些帧只靠 IMU/Wheel 传播。
本轮未统计这 67 帧对最终误差的贡献，也未做"是否误拒"的判定。

## F4 — C4 窗口未进入本轮闭环

C4_22…25 位于约 397 s，`bindingslap.json` 覆盖 273.556–346.906 s；
C4 段的连续绑定（raw cloud + cdr）在 `bindings20stop/40/60` 中也不覆盖 397 s。
因此**无法用现有绑定构造 397 s 的真实闭环**。
回答 C4 相关问题只能沿用 G1-C 的冻结 Seed 反事实结果，不能冒充闭环。

## F5 — 未做故障注入与 C++ 15D

按任务 §7.1 要求的丢失/延迟/超时注入、以及 C++ 15D 移植，本轮均未实施。
理由：在 F1 修复前，注入实验的结论同样会被回放器噪声污染。

## F6 — FAR-LIO 移植只做判定，未落地

`G2_FARLIO_ENGINEERING_AUDIT.md` 给出 20 条判定，本轮**没有**把任何一条移植进主基线，
因为任何移植都会与 F1 的不确定性混在一起，无法归因。
