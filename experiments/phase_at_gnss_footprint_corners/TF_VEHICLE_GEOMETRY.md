# AT2 — Vehicle reference and geometry provenance

**VERIFIED source semantics:** race URDF explicitly defines base_link at rear axle ground projection. `front_wheel` is the front axle reference, not one of four tyre centres. Recorded translations and front-axle/Bosch/VectorNav rotations agree with the historical project copy; LiDAR rotations differ (maximum .023rad) and the recorded values remain authoritative; see static_audit.json. AR state position is Bosch-origin in map with base-axis attitude. Every prior/posterior position is translated to rear axle using its own rotation. Production poses use their recorded base reference; their dynamic map→base TF is never applied to the new estimator.

Current URDF has a remote EAV25 visual mesh, no collision geometry or four tyre/contact links. Its commented box is not active physical geometry. A historical project copy retains an **active visual box** with documented origin, allowing conditional footprint experiments without inventing dimensions. bind_static.py reads this box into a private binding; dimensions are not published. A visual box is neither measured body outline nor tyre envelope and its agreement with the actual historical EAV24 vehicle is unverified. Current controller/planner widths are not substituted for body/tyre measurements.

Antenna1/2 and VectorNav ENU links are supplied only by the explicit historical candidate, absent from bag static TF. Antenna phase centre relative to VectorNav housing and rear axle is not independently surveyed. Full orientation is used, with correct transform direction; known shared TF agreement cannot certify missing antenna transforms.

**NOT_VALIDATED:** four wheel offsets, contact patch dimensions, historical tyre widths, steering-to-front-wheel dynamic TF and steering-angle calibration, physical body outline and continuous swept envelope. Neither rear/front axle points nor a visualization mesh is called tyre outer edge. No artificial four wheel footprints are generated. Actual tyre compression, suspension and road contact geometry are outside available data.

Geometric code accepts caller-provided private body/tyre polygon sets with a qualification label. It transforms each polygon by each estimator's own T_map_base and checks every boundary segment, crossing/touching, containment and enclosed track holes. Eleven new tests exercise nonplanar lever compensation, sparse long-edge crossing, contact, outside polygons, enclosed holes and parallel/collinear segments. Tests validate geometry algorithms; they do not supply missing physical calibration.
